# Plane20: U-Net → центры → независимые полные маски

Новый эксперимент в том же серверном окружении:
`kisor@dexter:/raid/kisor/projects/zb/plane20_stardist`.
Полное обучение при подготовке не запускается. Модели `runs/first` и
`runs/wide64`, исходные сцены и их перекрытия сохраняются.

## Запуск

```bash
ssh kisor@dexter
cd /raid/kisor/projects/zb/plane20_stardist/src
CUDA_VISIBLE_DEVICES=1 bash training/plane20/run_center_mask_training.sh
```

Результаты: `runs/center_mask32`. Продолжение:

```bash
CUDA_VISIBLE_DEVICES=1 bash training/plane20/run_center_mask_training.sh --resume
```

По умолчанию: 100 эпох, batch32, 200 шагов/эпоху, validation16batch.
Это те же **6400 train-кропов и 512 validation-кропов на эпоху** и то же
число обновлений оптимизатора, что у предыдущих моделей. Размер128×128,
halo16, seed42, разбиение сцен, порядок кропов и нормализация P5–P95
сохранены. Начальная LR3e-4, Adam с clipnorm5, LR уменьшается вдвое
после8эпох без улучшения val_loss, минимум1e-6.

Нужна одна A100, выбираемая `CUDA_VISIBLE_DEVICES`. Multi-GPU для этого
первого варианта намеренно не поддерживается: ROI содержат индексы
изображений в общем batch. Старые команды StarDist по-прежнему работают.

## Архитектура

- Общий U-Net глубины3 с базовой шириной32: **1 392 160 параметров**
  у всей модели. Используется существующий блок U-Net из csbdeep.
- Детектор выдаёт heatmap центров на исходной пиксельной сетке и2канала
  субпиксельных поправок.
- Для каждого центра извлекается окно **24×24** из общих признаков и
  исходного нормированного изображения. Добавляются2канала координат
  относительно именно этого центра.
- Общая небольшая mask-head выдаёт независимую sigmoid-маску для каждого
  объекта. U-Net не запускается повторно для каждой сомы.

Один пиксель может быть положительным в нескольких экземплярах.
Выбора владельца пикселя, обрезки соседними сомами и NMS по площади масок
нет. Генератор, геометрия, шум и политика видимости не менялись: в целях
по-прежнему находятся все сгенерированные сомы.

## Цели и loss

1. **Центры:** modified focal loss по CenterNet-подобной Gaussian heatmap
   sigma0.7px. Истинные центры — положительные пики; Gaussian снижает
   штраф отрицательных пикселей рядом с ними. Это не мягкая probability
   цель старой StarDist-модели.
2. **Субпиксельная поправка:** L1 в точках истинных центров.
3. **Каждая полная маска отдельно:** weighted BCE с pos_weight4 плюс
   soft Dice. Суммарный loss — сумма этих четырёх составляющих с весами1.

Лишние центры штрафуются детекторным focal loss. Hungarian matching в
train-loss не используется. Однозначное сопоставление применяется при
instance-оценке, как и раньше.

Центры обучаются по всем GT-сомам в центральных96×96. Для mask-head
на каждом посещении кропа выбираются до **64 сом** без возвращения,
равновероятно, с воспроизводимым seed. Это ограничивает вычисления;
остальные сомы не объявляются фоном и могут попасть в следующую выборку.
Для масок seed центра получает jitter sigma0.35px, ограниченный±0.75px,
чтобы decoder переносил небольшую ошибку детектора. GT при этом остаётся
на исходных координатах. В validation jitter отсутствует.

Пустые ROI для выравнивания размера batch имеют вес0. Фиксированное
число ROI предотвращает autotuning cuDNN на каждом новом числе сом.
Цели heatmap и полные26×26патчи масок кэшируются в RAM по сценам.
Во время обучения24×24маски вырезаются с нужным целочисленным сдвигом,
а не растрируются заново. Эти кэши строятся один раз при чтении сцен;
дисковый radial-cache StarDist для этой модели не нужен.

Первая эпоха включает чтение сцен, создание RAM-кэшей и компиляцию TF.
По отдельной проверке все444383сомы текущего датасета помещаются в ROI
даже с максимальным jitter: максимальный extent10.034px при half-size12.
Если другой датасет содержит слишком большие сомы, код явно остановится
вместо молчаливой обрезки GT.

## Проверка после обучения

```bash
source training/plane20/activate.sh
python -m training.plane20.center_inference evaluate \
  --run ../runs/center_mask32 --data ../dataset --split val \
  --crops 24 --start-index 32 --seed 991 \
  --threshold 0.3 --mask-threshold 0.5 \
  --output ../runs/center_mask32/validation_instances.json
```

Отчёт содержит три разные проверки:

- `predicted_centers`: итоговые маски с **предсказанными** центрами,
  однозначное сопоставление полных пересекающихся масок при IoU≥0.5.
- `oracle_centers`: диагностическое качество mask-head, которой даны
  **истинные GT-центры**. Это не метрика развёртываемого детектора.
- `center_detection`: precision/recall/F1 центров с допуском2px и
  однозначным сопоставлением.

Так отделяются ошибки обнаружения от ошибок восстановления маски.
`val_mask_dice_loss` в train-логе также использует GT-центры и подвыборку
масок. Его нельзя принимать за качество всего конвейера.
Общий новый loss численно несопоставим с loss старого StarDist.

Порог центра0.3 — исходная настройка, не результат калибровки. Его и
порог маски0.5 нужно подобрать на validation; итоговый test применяется
после фиксации параметров. Для сопоставления с предыдущей диагностикой
используйте те же seed991, start-index32, crops24. Начальные validation
кропы для настройки порогов можно задать `--start-index 0 --crops 16`.
Значения `--nms` у новой модели нет.

Предсказание реального кадра:

```bash
python -m training.plane20.center_inference predict \
  --run ../runs/center_mask32 --image ../assets/real_frame500.tiff \
  --threshold 0.3 --mask-threshold 0.5 \
  --output ../runs/center_mask32/real_frame500
```

Сетка128×128 с центральной областью96×96. Кандидаты — локальные максимумы
heatmap3×3, поправка ограничена±0.5px. Маски не подавляются из-за пересечения.
После объединения плиток удаляются лишь почти совпавшие центры в пределах1px.
Сохраняются полные sparse-маски `instances.npz`, `overlay.png` и
однослойный `labels_preview.tiff` только для просмотра.

## Ограничения и технические проверки

Это следующий эксперимент, а не подтверждённое улучшение real-data accuracy.
Слабые или почти неразличимые экземпляры всё ещё могут быть пропущены.
Один исходный пиксель кодирует один центр; модель не рассчитана на два
центра в одном пикселе. В текущем наборе таких конфликтов нет.
Почти совпадающие центры могут конкурировать при выделении локальных пиков.

Проверены полные маски пересекающихся экземпляров, перенос ROI без
изменения GT, границы, пустые batch, точное извлечение native пикселей,
суммирование градиентов перекрывающихся ROI и совместимость прежних
кропов/целей StarDist. Данные переделывать не нужно.

Технические запуски находятся только в `verification/center_mask_*`.
На двух фиксированных кропах после500обновлений soft Dice масок при
GT-центрах≈0.865. Это проверка обучаемости и координат, а не generalization.
В `verification/center-mask-verification.json` сохранены подробности;
`center-mask-data-contract.json` содержит проверку всех сцен и сравнение
прежних кропов. Проверены resume, instance-оценка и tiled inference.

```bash
python -m unittest discover -s tests -p 'test_plane20*.py' -v
```

Парный эксперимент плотность × шум и общий запуск четырёх моделей: [README_ABLATION.md](README_ABLATION.md).

## Смешанное обучение на рендерах под медиану

Один NPZ содержит `image` и `image_structured` с общей геометрией, центрами
и полными масками. Загрузчик чередует стили по индексу кропа. При чётном
batch size половина кропов в каждом батче берётся из каждого стиля. Оба
рендера каждой сцены принадлежат одному split. Разные сцены получают
собственные координаты сом и реализацию фоновой текстуры.

```bash
python -m training.plane20.generate_median --export-profile median_profile.npz
python -m training.plane20.generate_median --profile median_profile.npz --output dataset_median_mix
python -m training.plane20.train_center_mask --data dataset_median_mix --output runs/median_mix \
    --epochs 4 --steps 80 --val-steps 8 --batch-size 16 --max-masks 40
```

Для экспорта используются локальные калибровки медианы, размеров сом и
свечения. После экспорта генератору нужен только NPZ профиля. Структурный
рендер включает локальное ослабление пересвета Plane20 и случайные области
плавной засветки. У размещённых сом с запасом помещается полная маска в
24×24, включая смещение seed при обучении. Это отдельная синтетическая
проверка. Перенос на реальные записи оценивается по реальной разметке.
